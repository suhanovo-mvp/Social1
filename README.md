# Social1

Управленческая платформа системных инноваций ДТСЗН — цифровая реализация экосистемы
ускоренного выявления, разработки, тестирования и внедрения инициатив сотрудников
учреждений Департамента труда и социальной защиты населения.

Конечный продукт платформы — не база предложений, а поток реально внедрённых
улучшений социальных услуг и административных процессов.

## Запуск

Требуется Node.js версии 22.5 или новее. Внешних зависимостей нет — платформа
использует встроенные модули Node.js, включая `node:sqlite`.

```bash
npm run seed
```

```bash
npm start
```

Портал открывается по адресу `http://127.0.0.1:3000`.

Порт и адрес меняются переменными окружения `PORT` и `HOST`.
Полная перезагрузка демонстрационных данных — `npm run reset`.
Путь к файлу базы переопределяется переменной `SOCIAL1_DB`.

Автоматические тесты:

```bash
npm test
```

## Жизненный цикл инициативы

Управление построено по модели Stage-Gate: работы отделены от принятия решений.
Каждый этап завершается формальной точкой, где уполномоченный участник на основе
доказательств принимает решение **Go**, **Kill**, **Hold** или **Redirect**.
Каждое решение фиксируется с обязательной аргументацией — это формирует архив
знаний для будущих инициатив.

| Этап ТЗ | Стадия в системе | Gate | Кто решает | SLA |
|---|---|---|---|---|
| 1. Фиксация проблемы | Фиксация проблемы | — | автоматический переход | — |
| 2. Оценка и экспертиза | Оценка руководителем | Gate 1 | Руководитель учреждения | 3 рабочих дня |
| 2. Оценка и экспертиза | Экспертиза ДТСЗН | Gate 2 | Комитет экспертов ДТСЗН | 5 рабочих дней |
| 3. Разработка прототипа | Разработка MVP | Gate 3 | Команда разработки | 4 спринта по 2 недели |
| 4. Пилотирование | Пилотирование | Gate 4 | Координатор пилотов | 1 месяц + 1 неделя анализа |
| 5. Масштабирование | Масштабирование | Gate 5 | ДТСЗН | начало в течение 2 недель |

Этап 2 по ТЗ содержит две последовательные точки принятия решений, поэтому в
конвейере он представлен двумя стадиями. Соответствие этапам ТЗ показано в
интерфейсе на каждой карточке.

Сроки, критерии Gate, ответственные роли и перечень допустимых решений — не
отдельная настройка, а часть схемы процесса. Конвейер собирается из опубликованной
модели сквозной схемы «Полный цикл»: правка её этапов меняет реальную работу
платформы. Изменить их можно двумя путями — быстрой правкой в разделе «Настройки
платформы» или предложением об изменении, которое проходит обсуждение и
согласование. Оба пути пишут в одну модель, поэтому история изменений полная
независимо от того, кто и как их внёс.

## Функциональные модули

**Совместное проектирование процессов.** Схема процесса на платформе — не картинка
в справочнике, а описание того, как работа идёт на самом деле, и источник истины
для конвейера. Сотрудник, который каждый день упирается в лишний шаг, может не
писать служебную записку, а показать на схеме, что именно убрать.

Обсуждение привязано к шагу, а не к процессу целиком: замечание висит меткой на
конкретной фигуре, и разговор о ней не тонет в общей ленте. Предложение об
изменении несёт готовую черновую версию схемы, а не текст пожеланий, — обсуждают
и утверждают ровно то, что будет опубликовано. Правка идёт в редакторе поверх той
же схемы, что и просмотр: сетка дорожек и колонок сохраняет читаемость, поэтому
схема, собранная сотрудником, выглядит так же, как нарисованная проектировщиком.

Состав согласующих не задаётся списком должностей, а выводится из самого
изменения: сравнение версий показывает затронутые дорожки, а за ними стоят роли.
Изменение, которое меняет работу руководителя, требует его согласования; правка,
трогающая только расположение фигур, не поднимает никого. Изменение конвейера
инициатив дополнительно проходит через центральный аппарат. Согласование живёт по
тем же правилам, что и точки принятия решений: срок, задача в личном кабинете,
эскалация просрочки, обязательная аргументация при отказе.

Согласованная версия публикуется — и с этой минуты платформа работает по
предложению сотрудника: из блоков этапов опубликованной схемы пересобирается
конфигурация Stage-Gate, то есть сроки, ответственные и критерии реальных решений.
Публикация защищена: этап, на котором стоят живые инициативы, нельзя ни убрать, ни
переномеровать — сравнение идёт по узлу схемы, а не по номеру, поэтому подмена
этапа сдвигом нумерации тоже отклоняется. Опубликованная версия неизменяема, вся
история правок сохраняется, каждое действие попадает в журнал аудита.

Вклад в перестройку процессов измеряется теми же очками и тем же рейтингом, что и
советы по чужим идеям: замечание, признанное полезным, предложенное изменение,
согласование и вступление в силу. Отдельного механизма мотивации для этого нет.

**Идеи и решения.** Быстрый вход в экосистему и её самая массовая часть.
Сотрудник фиксирует проблему за минуту — форма из трёх полей с быстрыми
шаблонами, автосохранением черновика и подсказкой о похожих идеях. Коллеги
предлагают варианты решения и делятся проверенным опытом, который у них уже
сработал. Автор идеи отмечает то, что помогло; коллеги подтверждают рабочие
решения; модератор проверяет идеи и подтверждает опыт.

За полезный вклад социальные советники получают очки по настраиваемым правилам, из которых
складывается рейтинг за месяц, квартал и год, знаки отличия и — главное —
список сотрудников, рекомендованных руководителю к поощрению. Система фиксирует
рекомендацию, а не факт выдачи: решение принимает руководитель, а меры подобраны
под правила государственной службы — от благодарности и грамоты до
дополнительного дня отдыха, обучения и кадрового резерва.

Статусы идеи — «Новая», «На рассмотрении», «Принята к обсуждению», «В работе»,
«Реализована», «Отклонена», «Архив». Идея, для которой нужен полноценный проект,
поднимается до инициативы и уходит в конвейер Stage-Gate: за решением сохраняется
авторство, а идея получает сроки, этапы и точки принятия решений.

**Быстрое ревью предложений.** Отдельный режим для тех, у кого есть пять минут,
но нет времени читать обсуждения: система показывает по одной карточке решения,
оценка ставится одним движением. Свайп вправо — «полезно», влево — «пропустить»
с необязательной причиной, вверх — «в избранное», тап — подробности; на компьютере
то же делают стрелки, и все жесты продублированы кнопками. Очередь подбирает
предложения, которые видели реже всего, — так ни одно решение не остаётся
незамеченным. Оценки поднимают предложение в «Топ предложений», который модератор
разбирает первым, но очков автору не начисляют: это триаж, а не признание вклада,
и потому накрутка бессмысленна.

Модуль защищён от накруток: повторное начисление невозможно на уровне базы
данных, самооценки не учитываются, дубли решений отсекаются при отправке,
подтверждения коллег ограничены пределом, а модератор может отменить начисление
с записью причины в журнал. В ревью добавлены пределы частоты оценок и сигналы
модератору о серийных непрочитанных оценках и работе нескольких учётных записей
с одного устройства. Подробности — в инструкциях
[пользователя](docs/ideas-user-guide.md) и [администратора](docs/ideas-admin-guide.md).

**Управление инициативами.** Стандартизированная форма подачи, уникальный номер,
страница полного жизненного цикла со всеми решениями и комментариями, поиск и
фильтрация по статусу, этапу, направлению и учреждению. Подписка на инициативу
включает уведомления о каждом её шаге.

**Движок бизнес-процессов.** Автоматическая маршрутизация между участниками,
создание задач в личных кабинетах, уведомления, таймеры SLA с предупреждением о
риске превышения и автоматической эскалацией просроченных решений координатору.

**Управление проектами.** Agile-доски со спринтами и бэклогом продукта,
перетаскивание задач между колонками, оценки в story points, хранилище
технической документации.

**Пилотирование.** Заявки учреждений на роль площадки, ведение пилота, мониторинг
KPI с базовым, целевым и фактическим значением, встроенные опросы сотрудников и
граждан.

**Конструктор форм и опросов.** Анкета собирается в интерфейсе, а не правкой
исходников: одиннадцать видов вопросов (короткий и длинный текст, один вариант,
несколько вариантов, выпадающий список, шкала, число, дата, почта, телефон,
разделы блоков), справочники в качестве вариантов ответа, вариант «Другое» со
своим текстом.

Условие показа задаётся у самого вопроса и работает одинаково в браузере и на
сервере: «уточните, где именно» показывается только тому, кто оценил решение на 3
и выше. Скрытый вопрос не считается обязательным, а ответ на него не сохраняется —
поэтому оценка, изменённая в последний момент, не оставляет за собой ответов на
вопросы, которых человек больше не видит. Условие вправе ссылаться только на
вопросы выше по форме — на сохранении это проверяется.

Форма публикуется участникам платформы или ссылкой наружу: страница по ссылке
открывается без входа в систему, и её можно разослать в учреждения, у сотрудников
которых нет учётной записи. Настраиваются анонимность, один ответ от участника,
срок сбора и текст после отправки; начатую анкету можно сохранить черновиком и
вернуться к ней позже.

Результаты сводятся сразу: распределение по вариантам, среднее и медиана по
шкалам, свободные ответы целиком, таблица анкет построчно и выгрузка в CSV.
У условных вопросов рядом с числом ответов показан охват — скольким людям вопрос
вообще показывался, — иначе доля отвечающих врёт.

Образцом в поставке идёт опросник ДЗМ «Оценка потенциала переиспользования
ИИ-решений в учреждениях ДТСЗН»: пять блоков, 25 вопросов, оценка пяти решений по
шкале и восемь условных уточнений об эффектах. Он собран целиком в конструкторе —
это и есть проверка того, что движок покрывает реальные требования.

**Каталог разработчиков ИИ-решений.** Кому можно поручить разработку и
внедрение: внешние вендоры, внутренние команды и команды, которые может выделить ДИТ.
Все три вида живут в одном каталоге — их приходится сравнивать между собой. Каталог
фильтруется по виду разработчика, компетенциям в ИИ, соответствию требованиям
госсектора (реестр отечественного ПО, 152-ФЗ, ФСТЭК, закрытый контур, опыт
госзаказа), отраслевому опыту, загрузке и статусу; сортируется по оценке, числу
проектов и решений, размеру команды, заполненности. В карточке — портфолио
выполненных проектов, решения и технологии, оценки по итогам совместной работы и
журнал взаимодействий. Вкладка «Решения и технологии» ищет решение от потребности,
а не от вендора. До четырёх разработчиков сравниваются в одной таблице; подборка
выгружается в CSV.

Раздел рассчитан на ввод с нуля: у карточки считается заполненность и видно, чего
в ней не хватает; сведения старше полугода помечаются для сверки; при вводе
проверяются дубли по ИНН и названию; на сводке видны компетенции, которых нет ни
у одного разработчика. Сведения о подрядчиках коммерчески чувствительны, поэтому
каталог виден только по отдельному допуску: администратор каталога выдаёт
конкретному сотруднику роль пользователя, модератора или администратора каталога
прямо в разделе, без доступа к настройкам платформы.

Обязанности по карточке разделены. Базовые сведения — вид, название, реквизиты,
контакты, статус отбора, ориентир стоимости — ведёт модератор каталога. Технологический
профиль, портфолио и решения может заполнять представитель самой компании:
модератор привязывает к карточке учётную запись поставщика, и в его меню появляется
«Моя компания в каталоге». Представитель видит только свою карточку — без каталога,
оценок коллег, журнала контактов и статуса отбора. Его правки видны сразу, но с
пометкой «ожидает проверки»; тот, кто ведёт контакт, получает уведомление и
подтверждает сведения. Каждое изменение пишется в журнал аудита.

В разделе скачиваются три инструкции в PDF — пользователя, модератора и
администратора, представителя разработчика. Они собираются на лету из схем
процессов, справочников каталога и содержания в `server/guides/`, поэтому номера
шагов в инструкции совпадают со схемами и туром.

Демонстрационный набор — по три вымышленных разработчика каждого вида с
портфолио, решениями, оценками, журналом и представителем — входит в `npm run seed`
и ставится в существующую базу отдельно. Карточки помечены «демо» и удаляются, не
задевая введённых вручную:

```bash
npm run seed:providers
```

```bash
npm run seed:providers:remove
```

**Аналитика и КПЭ.** Три группы показателей из ТЗ: вовлечённость и культура;
скорость и эффективность; качество и риски. Воронка Stage-Gate, динамика подачи и
внедрения, сравнение учреждений, выгрузка отчёта в CSV.

**Сообщество.** Тематические обсуждения, профили участников с вкладом и
признанием, библиотека лучших практик с материалами для самостоятельного
внедрения другими учреждениями.

**Администрирование.** Настройка конвейера, управление участниками и
организациями, журнал аудита, контроль SLA, состояние системы.

**Презентация платформы.** Администратор скачивает в «Настройках платформы»
презентацию в PDF — слайды 16:9 о функциональности платформы. Счётчиков записей из
базы в ней нет: она одинаково читается на демонстрационной и рабочей базе.

Первый слайд — всегда титул концепции: «Концепция единой цифровой платформы для
комплексного управления реинжинирингом социальных процессов», автор концепции с
фотографией и должностью и перечень компонентов платформы. Сведения об авторе
лежат в `PRODUCT.author` в `server/presentation-deck.js`, фотография — в
`assets/presentation/author.jpg`.

Сначала — как компоненты работают вместе (путь проблемы до внедрённого решения,
то, что его питает, и то, что закрепляет результат), чего с помощью платформы
достигают и кто работает на ней вместе. Затем каждый из двенадцати компонентов
тремя слайдами: обзор со скриншотом, ключевые экраны и верхнеуровневая схема
совместной работы учреждений — дорожки участников (учреждение-автор, другие
учреждения, ДТСЗН, разработчики, пилотная площадка, платформа), шаги и связи.

Содержание лежит в `server/presentation-deck.js`, скриншоты — в `assets/presentation`.
Кадры снимаются с работающего портала скриптом без зависимостей — он управляет
установленным Google Chrome по DevTools Protocol:

```bash
SOCIAL1_URL=http://127.0.0.1:3000 npm run screens
```

Снимать стоит на свежих демонстрационных данных: подписи к кадрам рассчитаны на
демо-набор. Тест сверяет разделы презентации с меню и маршрутами портала, проверяет
наличие каждого кадра и корректность схем, поэтому новый раздел не может остаться
неописанным, а описанный — без скриншота.

**Схемы процессов.** Отдельный раздел с детализированными моделями в нотации BPMN —
тридцать одна схема, разделённая на **четыре пользовательских пути**. На схемах видны дорожки
ответственности, потоки управления и сообщений, точки принятия решений со всеми
ветвями и сроки по SLA. Любую схему можно разобрать по шагам: подсказки подсвечивают
элементы прямо на диаграмме и объясняют, что происходит на каждом шаге и почему
именно так. У каждого пути своя матрица ответственности — кто из ролей что делает.

*Путь 1 — подача полноценной инициативы* (14 схем): проблема требует проекта,
и она проходит конвейер Stage-Gate от формулировки до тиражирования.

*Путь 2 — обсуждение идей* (6 схем): проблема мешает каждый день, но проекта
не требует — решение уже есть у коллег. Быстрая подача, предложения решений,
ревью карточками, модерация, рейтинг и поощрения. Идея, для которой всё-таки
нужен проект, поднимается до инициативы и переходит в первый путь.

*Путь 3 — каталог разработчиков ИИ-решений* (5 схем): подбор исполнителя под
задачу, добавление разработчика, ведение карточки, работа представителя компании
и выдача доступа к каталогу. Схемы дописаны в конец альбома, поэтому номера
разделов двух первых путей не сдвинулись.

*Путь 4 — совместная работа с процессами, знаниями и опросами* (6 схем):
изменение процесса от замечания на шаге до вступления в силу, согласование
изменения владельцем затронутой дорожки, проект решения от черновика до базы
знаний, переход от принятого решения к задаче разработки и обратно к
зафиксированному решению, сборка анкеты для учреждений и её заполнение по ссылке.
Путь дописан после каталога — разделы 1–25 сохранили свои номера.

Разделы и шаги пронумерованы сквозным образом: схема — это раздел с номером от 1
до 31, каждый её элемент — шаг вида «4.6». Номер виден на самой фигуре, в перечне
схем, в разборе и в выгруженном PDF, поэтому на конкретный шаг можно сослаться
в регламенте.

**Выгрузка в PDF.** Схема выгружается векторным PDF: текст в файле ищется и
копируется, нумерация сохраняется. Под схемой печатается пошаговое описание
процесса — то же, что показывает разбор на экране: номер шага, его название и
пояснение, разложенные по колонкам. Формат листа подбирается по размеру схемы —
A3 для большинства, A2 для сквозного процесса. Альбом всех схем собирается одним
файлом с титульным листом и содержанием, разбитым по пользовательским путям
и владельцам процессов; путь схемы напечатан в шапке каждого листа.
PDF формируется на сервере без внешних библиотек: шрифт PT Sans встраивается
как CIDFontType2, поэтому кириллица отображается и ищется корректно.

данных диаграммы: 136 шагов по двадцати пяти схемам. Обучение по схеме объясняет
модель процесса, обучение по интерфейсу — где выполнять эти шаги в портале.

## Система метрик

**Группа 1 — процесс, вовлечённость, культура.** Количество зарегистрированных и
внедрённых инициатив, прохождение каждого Gate, уровень вовлечённости сотрудников,
вовлечённость в голосование и лидеры поддержки, участники пилотов, доля
масштабирования «снизу», валоризация эффекта.

**Группа 2 — эффективность и скорость.** Скорость полного цикла «проблема →
масштабирование» (среднее и медиана), время прохождения каждого этапа в сравнении
со стандартом обслуживания, коэффициент успешности пилотирования, время до первого
решения.

**Группа 3 — качество и риски.** Количество решений Kill, Redirect и Hold, риск
«заморозки» инициатив, распределение остановок по этапам. Решения Kill не являются
негативным показателем: они означают, что система отсеивает нежизнеспособные
проекты и экономит ресурсы.

## Ролевая модель

Роли, права и их привязка к участникам хранятся в базе, а не в коде: администратор
заводит роль, передаёт право и назначает участнику дополнительные роли без правки
исходников и пересборки. Участник может держать несколько ролей — его права
складываются из всех. Семь ролей платформы и их полномочия заведены значениями по
умолчанию при первом запуске.

Дорожка схемы связывается с ролью, и эта связь работает: из неё выводится состав
согласующих для каждого изменения процесса.

## Роль искусственного интеллекта

ИИ поддерживает человека, но не принимает решения на Gate. Все алгоритмы
объяснимые: система показывает не только результат, но и факторы, которые к нему
привели.

- **Классификация инициатив** по тематическим направлениям с указанием признаков,
  по которым сделан вывод.
- **Поиск похожих инициатив** при подаче — предотвращает дублирование усилий.
- **Анализ обратной связи** пилотов: тональность, ключевые темы, проблемные сигналы.
- **Прогноз успеха** с раскрытием каждого фактора и его вклада в оценку —
  включая поддержку коллег как независимый сигнал востребованности решения.

## Безопасность

- Пароли хранятся в виде scrypt-хэшей с индивидуальной солью.
- Сессии в HttpOnly-cookie с флагом SameSite=Strict.
- Ролевая модель доступа проверяется на сервере при каждом запросе; права
  интерфейса носят вспомогательный характер.
- Журнал аудита неизменяем: записи связаны цепочкой SHA-256, изменение или
  удаление задним числом ломает цепочку и выявляется проверкой целостности.
  Защита продублирована триггерами базы данных.
- Заголовки безопасности, включая строгую политику Content-Security-Policy.

Платформа спроектирована с учётом будущего расширения: слой API отделён от
интерфейса, модули независимы, конфигурация процесса вынесена в данные — причём
не в отдельную настройку, а в редактируемую модель процесса, из которой она
и собирается. Каталог `shared/` содержит модели, общие для браузера, сервера и
выгрузки в PDF: схема, принятая проверкой в редакторе, не может быть отвергнута
публикацией по другой причине.
Открытые REST-эндпоинты позволяют интегрировать платформу с кадровыми системами
и порталами государственных услуг без изменения ядра.

## Сторонние материалы

Шрифт PT Sans (ParaType) распространяется по лицензии SIL Open Font License 1.1;
текст лицензии — в `assets/fonts/OFL.txt`. Шрифт используется только для выгрузки
схем в PDF. Других сторонних материалов и npm-зависимостей в проекте нет.

## Ограничения демонстрационной версии

- Хранилище — SQLite в файле `data/social1.db`; для промышленной эксплуатации
  требуется СУБД с репликацией и шифрованием на уровне хранения.
- Интеграции с внешними системами ДТСЗН не реализованы — по ТЗ на данном этапе
  они не требуются.
- Уведомления доставляются внутри платформы; электронная почта и SMS не подключены.
- Загрузка файлов ограничена ссылками на материалы.
- Форма, опубликованная по ссылке, принимает ответы без подтверждения личности:
  защита от массовой автоматической отправки (ограничение частоты, капча) на этом
  этапе не ставилась — ссылка рассылается по служебным адресам учреждений.
